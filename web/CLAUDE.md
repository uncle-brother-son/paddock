## What this repo is
- `web/` is one Next.js 16 app deployed to Cloudflare Workers with OpenNext (worker name `paddock`, currently https://paddock.paddock-55d.workers.dev). It serves:
  - the **customer website** (being built: the frame, and since W73b the pages Sanity holds: the home page at `/`, a content page at `/[slug]`, an info page at `/info/[slug]`);
  - **API routes** under `app/api/v1/*`, used by the Retool staff app, and the Stripe and Sanity webhooks. These are live. Do not change their contracts without agreeing it, because the staff app depends on them.
- `studio/` is Sanity Studio (v5). Project `qx4gqx7t`, dataset `production`. Content types: `contentPage`, `infoPage`, `blogPost`, `productFamily`, `sizeGuide` and the single documents `siteSettings`, `navigation`, `shopSettings`, `eventsSettings` (website only), plus `serviceType`, `product`, `addon`, `membershipPlan`, `sessionPassType`, `giftCardType`, `event`, `productCategory` (mirrored into Supabase). Shared blocks: `picture`, `media`, `richText`, `seo`, `linkTo` (`studio/schemaTypes/objects/`; a link goes to a page, an event, the shop, the gift card or an outside address). A content page is a list of **modules** (`hero`, `upcomingEvents`): the Hero is a module any page can use, never a field of the page (W73b). A product's, an event's and the gift card's pictures are galleries of `media` (an image or an MP4); the staff app's picture is the gallery's first image. The site reads them through `lib/sanity/read.ts` only. Words a page can't have as its address: `lib/routes/reserved-slugs.ts`, the one list both sides read. A document with a slug keeps its old ones (`previousSlugs`, added by the Studio's Publish action); a page that finds nothing at a slug asks `lib/sanity/redirects.ts` where it went.
- `supabase/` holds the migrations. Supabase project `paddock` holds bookings, customers, orders, memberships, credits and all live data.
- `project info/` holds the original scope, user flows and data model notes. What the rules should be is the Notion "Paddock Build Specification"; what they are is `web/server/rules/` and its tests.
- The staff tool is a Retool React app (`~/Documents/Code/paddock-retool-app`). It is not in this repo, and it holds screens only: the rules are here, in `web/server/rules/`.

## Test levels (WQ29, WQ30)
`npm run check:fast` reads the changed files (against `origin/main`, committed or not), prints the level and runs that level's checks. Money wins: one Level 1 file makes the whole change Level 1, and one Level 1b file makes a website change Level 1b. A brief keeps its Level 1b part apart from its Level 2 work.
- **Level 1, money and backend:** anything in `web/server/`, `web/contracts/`, `web/app/api/`, `supabase/`, `custom-worker.ts`, `wrangler.jsonc`; a package change; a website file that uses Stripe or server code (but `lib/shop/read.ts`, below); a Studio field the Worker's Sanity webhook reads (`WEBHOOK_FIELDS` in `scripts/check-fast-level.mjs`). The full process: the full Worker run once, planted bugs, an independent review, a full report. `check:fast` runs nothing: it names the files and exits 2.
- **Level 1b, backend that does not touch money (WQ30):** the Sanity webhook and its sync (`web/app/api/sanity/`, `server/rules/catalog/sanity-sync.ts`); a migration that names no money, booking or membership; a route under `/api/v1` that only reads and names none (`backendWithoutMoney` and `MONEY_WORDS` in `scripts/check-fast-level.mjs`; in doubt it is Level 1, and a Studio field the webhook reads is still Level 1). The shop's reads are Level 1b by name (WQ45; `SHOP_READ_PATHS`): `server/rules/shop/`, `contracts/shop.ts`, the availability route and `server/api-allowlist.test.ts`, for as long as they only read (one that writes a row, or a route that takes more than GET, is Level 1). Its checks: lint, `tsc` and the changed tests, which `check:fast` runs, then **one full Worker run** (`caffeinate -i npm run test:unit`), which it does not: it says the run is still owed and exits 2. No planted bugs, no independent review, a short report.
- **Level 2, website and Sanity:** the pages and components, the Studio's schema and desk, and (WQ45) `lib/shop/read.ts`, the one website file that imports the shop's reads: its import of `@/server/rules/shop/...` is not money code, there and in no other file. Lint and `tsc`, the changed `*.test.ts` files, and only the changed components' Storybook tests (accessibility included). No full Worker run, no OpenNext build, no planted bugs, no screenshots unless asked. Wayne's look in Storybook or on the preview is the check. Half-page report.
- **Level 3, a small visual fix:** no brief; Wayne says it directly. Edit, lint, that component's story test (`check:fast` runs the same as Level 2).

- **Focus and links (WQ12, WQ28):** every link and button has the keyboard-only focus ring from one rule in `app/globals.css`; never `outline: none` on one. The ring follows what the visitor last used, a key or a pointer (`components/frame/InputKind.tsx` notes it on `<html>` as `data-input`), not `:focus-visible` alone: a browser counts a clicked `<select>` as keyboard focus. A component that draws the ring round a control that is not seen (the Shop's ALL and SORT, a size's radio) uses the `has-keyboard-focus:` variant, never `has-[:focus-visible]:`. A link in running text is `TextLink` (`components/ui/`); a link with a design of its own uses `SiteLink`. `SiteLink` never fetches a page that is not built yet ahead of a press (`lib/routes/not-built.ts`: `/book`, `/account`, `/shop/gift-card` and the rest): when a page is built, take its address off that list (its test fails until then). Every button shows the hand (one rule in `app/globals.css`). **The shade behind a popup is `Overlay`** (`components/ui/Overlay.tsx`, Wayne's Figma Overlay: Object/Dark Shade since WQ48; `duration="long"` behind a panel that slides in over the long duration): never draw another. Chromium displaces the blurred page with the `OverlayTexture` filter the root layout draws once; Safari and Firefox get the blur with a grain layer, which is a layer of its own because nothing inside the shade can blend with the page behind. Playwright's WebKit does not draw backdrop blur in its screenshots, headless or not: look in Safari. Stacking: the header `z-10`, a popup's shade `z-20`, popups and "Skip to content" `z-30`, the grid overlay above them all at `z-40`.

Never type in a curve, an ease keyword, a spring or a duration: `lib/motion/typed-in-motion.test.ts` fails on one. Lenis (smooth scroll, off with reduced motion) and Motion's defaults are set once in `components/providers/MotionProviders.tsx`; a panel that scrolls by itself carries `data-lenis-prevent`. Use the installed `lenis` and `framer-motion`; GSAP or any other package only with Wayne's yes.

## Architecture (agreed at the start; the move finished at step G, the tests' move at step H, Nov 2026)
- This Worker is the ONE backend for both the website and the Retool staff app. Every booking, pricing, credit, order, payment, refund and admin action runs here; only this Worker talks to Stripe and the database. The staff app is screens only, calling `/api/v1/staff/...` through one Retool resource ("Paddock Worker v1"); the website calls `/api/v1/customer/...` and, with no sign-in, only the public routes `server/api-allowlist.test.ts` lists (`/api/v1/shop/availability`). A page reads the shop itself with `readShop()` (`server/rules/shop/reads.ts`): never a stock number or a Stripe id.
- `server/rules/` holds the rules and is **the source of truth for how bookings, orders, payments, refunds, memberships and the catalogue behave** (`server/rules/README.md` says what each slice decided and why). The old Retool code, its frozen copies and the golden files are gone (W61, W65).
- `app/api/` is `v1/` (each route through `defineRoute`: sign-in, permissions, input, idempotency) and two webhooks, `stripe/webhook` and `sanity/webhook` (each with its own signature check, on the Worker's own database connection; no service-role key). Nothing else: `server/api-allowlist.test.ts`.
- **Contracts** (`contracts/`, zod) are what the screens compile against: after any edit there, `npm run export:contracts` writes the staff app's `workerContracts.ts` (`npm run check:contracts` fails when it is behind).
- **Tests.** Each decision has a rule test beside its rule, on the live schema (`server/rules/testing/live-schema.sql`, generated from the live catalog, up to migration 034, and carrying 035, which the lead applies before the W72a push). The all-Worker sweep (`server/rules/testing/sweep/`) presses every scenario through the Worker as its screen does and compares it with its recording (`testing/recordings/`), with the money invariants checked on each. A recording is not a rule test: `UPDATE_RECORDINGS=1` would accept a change, so a new rule needs a test of its own. `server/staff-app-*.test.ts` read the staff app's files. No test reaches real Stripe.
- **Switches:** `ORDER_SWITCH` lists the kinds of action that are on; a kind off refuses (or, for `lapse_sweep`, pauses) and fixes go forward: there is no old code behind it.
- **Release order:** publish the staff app first when the published app still calls something the Worker removes or changes; deploy the Worker first when the staff app calls a route only the new Worker has. Each brief's report states the order and why.
- Database writes that must be all-or-nothing run in one Postgres transaction. Stripe calls are made outside transactions, always with an idempotency key (but `subscriptions.cancel`, a DELETE, which takes none), with a recorded pending state so a failure can be reconciled (every 5 minutes, `server/scheduled.ts`).
- What is left for the website build and for go-live: the W70 audit's two tables (staff app repo, `briefs/W70-audit-report.md`, point 6) and `briefs/W03-decisions.md`.

## Business rules the website must respect
These are enforced server-side in this Worker; the front end never computes them on its own. Full detail: claude.ai project doc `claude/paddock-website-backend-log.md`.
- **Ages:** every attendee is 18+. Only the account holder gives a date of birth (when attending, or buying a membership or pass). Guests give name and email only; the booker ticks "Everyone else in this booking is 18 or over" (required, checked on the server).
- **Session times:** stored as London wall-clock digits labelled UTC. Display them as stored (24-hour, e.g. 16:00); do not convert time zones. Credit and expiry checks use the London date.
- **Spaces are never held** (not in the bag, not at checkout). Everything is re-checked when checkout opens and again at Pay, before any charge.
- **Booking:** a customer can book for others (the booker need not attend); one booking per day is checked against the paying customer; party size can change in the bag and at checkout; a full session flagged in the bag stays there and is left out of checkout.
- **Members:** per-person price with "1 credit for you"; bands are Off-Peak, Core and Peak; add-on credits only for Herd members; a membership or pass bought in the same order can pay for a booking or event in that order.
- **Guest checkout:** a new email can buy anything (including a membership or pass). An email already on file can attach orders but never changes that customer's details or card; buying a membership or pass with it needs the emailed code.
- **Saved card:** one per customer; replacing it also updates every membership's renewal card.
- **Website payment methods:** card, Apple Pay and Google Pay only.
- **Payment order:** membership/pass credits, then store credit, then gift card, then card or wallet. A discount code reduces prices first (never gift cards or postage). Postage: Standard or Express, flat rate, free Standard over the threshold, UK only.
- **Customers online:** move or cancel a session booking up to 24 hours before (cancel = store credit, never a card refund online); add add-ons up to 2 hours before (no removal online); events cancel to store credit before the event's own cut-off.
- **Events:** members-only, public or members-first; Public / Pre-Herd / Herd prices; guests pay public; no session credits, no add-ons; not counted in one booking per day.

## Integrations

Website routes use the customer's Supabase session, never a staff key in the browser. Supabase's package is loaded for sign-in only (the anon key; four files, `server/no-service-role-key.test.ts`).
