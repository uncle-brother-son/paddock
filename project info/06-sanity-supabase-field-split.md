# 08. Sanity vs. Supabase — Field Ownership

## The rule

A field lives in **Sanity only** if it's pure marketing/display content — never read by checkout
logic, never needed by staff in Retool. It lives in **Supabase** if Retool needs to see/edit it,
or the backend needs to read it at checkout/runtime (price, stock, Stripe IDs). A small number
of **mirror fields** (name, one thumbnail image) are deliberately duplicated into Supabase —
cheap, low-maintenance, and they let staff identify a record in Retool without switching tools.

**This split only applies to "catalog" tables — content that's both client-authored in Sanity
*and* transactional.** Everything else (bookings, orders, customers, staff, issued gift cards,
membership/pass instances) was never Sanity content in the first place — it lives in Supabase
only, no duplication question applies. Marked clearly below.

Sync direction throughout: **Sanity is edited by the client → webhook on publish → backend
creates/updates the mirror row in Supabase.** Supabase is never the source of truth for content;
it's the source of truth for price, stock, and transactional state.

## Products / Merchandise — catalog table (needs the split)

**Sanity only** (content, fetched directly by the frontend, never touches Supabase):
- Description
- Product info (composition / made-in / etc.)
- Images (full array — no fixed limit)
- `productGroup` — a shared text value (e.g. slug like `"classic-tee"`) linking colour variants
  of the same underlying product together for frontend display only (e.g. showing a "also
  available in black" swatch on the white tee's page). Colour variants are separate Products in
  Postgres/Stripe with independent stock, price, and Stripe IDs — this field is purely a content/
  navigation relationship, read directly by the frontend, and never touches Postgres. Preferred
  over manual pairwise references between products because adding a new colour later only
  requires setting the same group value on the new product, rather than editing every existing
  variant's reference list.

**Supabase — mirrored from Sanity** (Sanity is the source of truth; webhook overwrites these on
every publish; never edited directly in Retool):
- Name
- `thumbnail_url` — Sanity + Postgres mirror (resized URL, generated from image[0])
- Category — mirrored for Retool filtering/navigation; authored in Sanity since it also drives
  frontend navigation, not independently editable in both places, to avoid drift

**Supabase — Postgres-owned** (set and changed directly in Retool; the Sanity sync never
touches these, even on republish):
- Product ID (auto-generated by Postgres)
- `sanity_product_id` (captured from Sanity's auto-generated document `_id` on webhook, used to
  match future publishes to the correct existing row rather than creating duplicates)
- **Base price, member price, sale price** — three independently priced tiers, deliberately
  *not* synced from Sanity. Price is operationally volatile (sales, corrections, member
  pricing) and staff need to change any tier in Retool instantly without a Sanity publish/
  webhook round-trip. Each tier has its own Stripe Price object under the same Stripe Product —
  a Retool edit to any one tier creates a new Stripe Price for that tier specifically (Stripe
  Prices are immutable) and writes it to that tier's own field. See 09-write-architecture.md
  for the full tier-selection priority (member always wins over sale; sale applies over base;
  promo codes apply on top of whichever tier was selected).
- Fulfillment method: shipping / pickup only / both
- Shipping weight/dimensions
- Stripe product ID
- Active flag
- No SKU on the Product record itself — SKU lives on the Variant, since a bare Product isn't
  directly sellable (see Variant, below)

**Product Variant** — fully Postgres-owned, no Sanity equivalent at all. A Product isn't
directly sellable on its own — the Variant is the real sellable unit, which is why SKU, stock,
and price override all live here rather than on the Product record. Every Product has at least
one Variant, even where there's no visible size choice on the frontend (e.g. a tote bag gets a
single "default" Variant), so SKU/stock/price always come from exactly one consistent place with
no special case to remember. Colour is *not* a Variant attribute — colour options are handled as
separate linked Products via `productGroup` (see above), not as a variant of one product.
- Variant ID, linked Product ID
- Size
- SKU
- Price override
- Stock quantity
- Stripe price ID

## Add-ons — catalog table (needs the split)

**Sanity only:**
- Name → mirrored, see below
- Description
- Product info (ingredients/composition)
- Images (full array — no fixed limit)

**Supabase — mirrored from Sanity:**
- Name
- `thumbnail_url` — Sanity + Postgres mirror (resized URL, generated from image[0])
- Category — same reasoning and mechanism as Products (mirrored, authored in Sanity)

**Supabase — Postgres-owned:**
- Add-on ID (auto-generated by Postgres)
- `sanity_addon_id` (captured from Sanity's auto `_id`, same mechanism as Product)
- SKU — sits directly on the Add-on record itself, since add-ons have no Variant layer beneath
  them (unlike Product, where SKU lives one level down)
- **Base price, member price, sale price** — same three-tier pricing model as Products, each
  with its own Stripe Price ID
- Active flag
- Stripe product ID

**Add-on order line** — fully Postgres-owned, no Sanity equivalent:
- Linked booking ID, add-on ID
- Quantity
- **Price at time of purchase** — a frozen snapshot of whichever price tier applied (base/
  member/discount), not a live reference to the current Add-on price. Needed because prices can
  change after the fact (a later sale, a correction) — without a snapshot, historical orders
  and receipts would silently show today's price instead of what the customer actually paid.
- **SKU** — also a frozen snapshot, same reasoning as price, in case a SKU is corrected later
- Stripe price ID
- Redemption source: paid directly / membership credit

## Session / Service Types — catalog table (needs the split)

"Public Session," "Private Session (60 min)," "Private Session (120 min)" each have marketing
copy shown on the Bookings page, and an operational price/duration/capacity read at booking
time. Full entity definition lives in `05-data-model.md` → 5.2 Bookings → Service Type; this
section covers only the Sanity/Postgres split.

**Sanity only:**
- Description
- Images (no fixed limit)

**Supabase — mirrored from Sanity:**
- Name
- `thumbnail_url` (resized URL, generated from image[0])

**Supabase — Postgres-owned:**
- Service Type ID (auto-generated)
- `sanity_service_type_id` (captured from Sanity's auto `_id`)
- Duration (minutes)
- Capacity (6 for public — real cap; 6 for private — blocking value only, see 5.2 Bookings for
  the full explanation)
- Booking type: public / private
- Price — public sessions only (flat per-person rate). Private sessions use a separate
  **Service Type Price Tier** table instead (banded by total headcount, not flat/per-person —
  see 05-data-model.md for the full structure and confirmed pricing data)
- Active flag
- Stripe product ID, Stripe price ID (public sessions only)

No category — too few service types to warrant a grouping mechanism.

Every generated **Session** references this Service Type ID rather than duplicating its price/
duration/capacity — Sessions and Bookings themselves are fully operational (see below), never
Sanity content.

## Everything else — no split needed, Supabase only

These were never Sanity content and don't need this treatment at all:

- **Bookings** (Session, Booking, Booking Guest) — generated/managed operationally, not
  client-authored
- **Gift Cards (issued instances)** — transactional records, not content, no split needed. A
  single representative image for the Gift Cards page (no design picker, no per-card artwork
  choice) is ordinary Sanity page content — see 05-data-model.md for where it lives. Not a
  database entity.
- **Orders / Checkout**
- **Customers / Accounts**
- **Staff / Admin Users**

## Practical effect on the sync webhook

The Sanity → Supabase sync webhook (triggered on publish) now writes slightly more than just
price/Stripe IDs for catalog tables — it also writes `name` and a single `thumbnail_url` per
record. Everything else stays exactly as originally designed: Sanity remains the only place
content is authored, Supabase remains the only place Retool and checkout logic ever read from.
